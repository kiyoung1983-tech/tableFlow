## 1. 목표와 최종 구성

Windows에서 신규 풀스택 서비스를 바로 시작할 수 있도록 다음 구조를 만들었다.

- 백엔드: Java 21 바이트코드, Spring Boot 4.1.0, Gradle 9.5.1 Wrapper
- 프론트엔드: React 19.2, TypeScript 6.0, Vite 8.2
- 데이터: PostgreSQL 17, Flyway, Spring Data JPA
- 선택 인프라: Redis 8 컨테이너(아직 애플리케이션에서는 사용하지 않음)
- 보안: Spring Security, 개발용 HTTP Basic, 쓰기 API 인증
- 테스트: JUnit 5, Testcontainers PostgreSQL
- 운영 기반: Actuator, Docker Compose, GitHub Actions
- 구조: `backend`와 `frontend`를 분리한 모노레포, Spring Modulith 포함

처음부터 마이크로서비스로 나누지 않고 모듈러 모놀리스로 시작한다. 배포·장애 격리·조직 경계 같은 실제 분리 근거가 생길 때 서비스를 떼어내기 위한 선택이다.

## 2. 1단계 — 기존 환경 진단

### 확인 방법

PowerShell에서 각 실행 파일의 위치와 버전을 조회하고 Docker 및 WSL 상태를 확인했다. 프로젝트 폴더에는 선행 소스가 없어서 새 골격을 생성해도 충돌하지 않는 상태였다.

### 진단 결과

- OS: Windows 10 Pro로 보고됨(내부 빌드 번호 조회는 제한됨)
- Git: 2.53.0.windows.3, Codex 번들 경로에서 사용 가능
- 기본 Java/Javac: Amazon Corretto 21.0.10 LTS
- 추가 JDK: OpenJDK 26 설치 확인
- Node.js: 24.15.0 LTS
- npm: 11.12.1
- Docker CLI/Desktop: 29.4.0 설치, 엔진은 정지 상태
- IntelliJ IDEA: 2026.1
- Gradle/Maven 전역 설치: 없음
- VS Code 및 winget: 명령 경로에서 확인되지 않음
- WSL 상태: 현재 실행 계정에서 `E_ACCESSDENIED`

Gradle은 전역 설치를 하지 않았다. 저장소에 포함된 Wrapper가 프로젝트별 Gradle 버전을 고정하므로 팀과 CI의 재현성이 더 좋다. IntelliJ가 이미 있으므로 VS Code도 추가 설치하지 않았다.

## 3. 2단계 — 도구 구성 결정

### Java 기준

기본 JDK 21이 이미 안정적으로 설치되어 있고 장기 지원 버전이므로 프로젝트의 컴파일 타깃을 Java 21로 정했다. JDK 26도 존재하지만 비-LTS이므로 애플리케이션 런타임 기준으로 채택하지 않았다. 신규 기능 실험은 별도 브랜치에서 진행하고 운영 기준은 LTS로 유지하는 선택이다.

빌드는 `sourceCompatibility`, `targetCompatibility`, `--release 21`을 함께 지정했다. 로컬 JVM이 달라도 Java 21 API와 바이트코드 범위를 넘지 않도록 하기 위함이다.

### Node 기준

설치된 Node 24 LTS를 그대로 사용했다. 프론트 패키지는 `package-lock.json`으로 고정하고 CI에서는 `npm ci`로 재현한다.

### 발생한 설치 관련 이슈

npm의 기본 캐시 경로가 Codex 샌드박스 밖이라 `EPERM`이 발생했다. 작업 폴더의 `work/npm-cache`를 임시 캐시로 지정해 해결했다. 사용자 전역 npm 설정은 변경하지 않았다.

## 4. 3단계 — 모노레포 생성

### 백엔드

Spring Initializr 메타데이터는 4.1.0 GA를 `4.1.0.RELEASE`로 반환했지만 해당 BOM 좌표가 존재하지 않아 생성 API가 HTTP 500을 반환했다. 실제 Maven 좌표인 `4.1.0`을 명시해 생성에 성공했다.

포함한 주요 스타터는 Web MVC, Validation, Security, Actuator, JPA, Flyway, PostgreSQL, Testcontainers 및 Spring Modulith다. 빌드 도구는 Gradle Kotlin DSL과 Wrapper를 선택했다.

### 프론트엔드

Vite의 React TypeScript 템플릿으로 생성했다. 개발 서버의 `/api`, `/actuator` 요청은 `localhost:8080`으로 프록시하여 개발 중 CORS 마찰을 줄였다. 화면에서는 백엔드 health와 Todo 목록을 호출해 연결 상태를 즉시 확인한다.

## 5. 4단계 — 애플리케이션 기본 골격

### PostgreSQL과 Flyway

루트 `compose.yaml`에 PostgreSQL 17 Alpine과 영속 볼륨, health check를 정의했다. Flyway의 `V1__create_todo.sql`은 UUID 기본 키, 제목, 완료 여부, 생성 시각을 가진 `todos` 테이블과 정렬용 인덱스를 생성한다.

Hibernate는 `ddl-auto=validate`로 설정했다. 스키마 변경 권한은 Flyway에만 두어 애플리케이션 실행 시 Hibernate가 운영 DB를 암묵적으로 수정하지 않게 했다. OSIV도 꺼서 웹 계층까지 영속성 컨텍스트가 새는 것을 방지했다.

### API와 보안

- `GET /api/todos`: 공개 조회
- `POST /api/todos`: 인증 필요
- `GET /actuator/health`: 공개
- 그 밖의 요청: 인증 필요

개발용 계정 기본값은 `developer / change-me-locally`이며 환경 변수 `DEV_USER`, `DEV_PASSWORD`로 덮어쓴다. 이것은 로컬 부트스트랩용이다. 운영에서는 사내 IdP 또는 외부 IdP의 OIDC/OAuth2 Resource Server로 교체해야 한다.

개발 CORS origin은 기본 `http://localhost:5173`이며 `CORS_ALLOWED_ORIGIN`으로 변경 가능하다. `/api/**`에 대한 CSRF 예외는 현재 Basic 기반 JSON API 개발을 위한 설정이다. 브라우저 쿠키 인증을 도입하면 CSRF 정책을 다시 설계해야 한다.

### Testcontainers

테스트용 PostgreSQL 이미지는 운영 로컬 버전과 맞춘 `postgres:17-alpine`으로 고정했다. `@ServiceConnection`으로 동적 포트와 JDBC 설정을 Spring Boot가 자동 연결한다.

첫 통합 테스트에서는 Hibernate가 Spring Modulith JPA의 `event_publication` 테이블을 찾지 못해 실패했다. Todo migration은 정상 적용됐지만 JPA starter는 event publication DDL을 자동 생성하지 않는 것이 원인이었다. Modulith의 `spring.modulith.runtime.flyway-enabled` 옵션도 확인했으나 이것은 모듈별 migration 경로와 실행 순서를 구성하는 기능이지 프레임워크 테이블을 생성하는 기능이 아니다. 따라서 Modulith 2.1 JPA entity mapping에 맞춘 `V2__create_event_publication.sql`을 명시적으로 추가했다. Hibernate 자동 DDL 대신 Flyway가 프레임워크 테이블까지 소유하게 하여 운영 스키마 변경 이력을 일관되게 유지한다.

### Redis 판단

Compose에는 Redis 8을 준비했지만 애플리케이션 코드가 아직 캐시나 세션을 사용하지 않으므로 Redis 스타터는 클래스패스에서 제거했다. 사용하지 않는 런타임 의존성을 미리 넣어두지 않는 선택이다. 실제 캐시 정책이나 세션 전략이 정해질 때 스타터와 테스트 컨테이너를 함께 추가한다.

### CI

GitHub Actions를 백엔드와 프론트엔드 병렬 Job으로 구성했다.

- 백엔드: Temurin Java 21, Gradle 캐시, 전체 테스트
- 프론트엔드: Node 24, `npm ci`, lint와 production build
- 권한: 저장소 읽기만 허용

## 9. Docker 엔진 준비 및 프로젝트 실행 원리

### 9.1 Docker Desktop을 실행한 이유

```powershell
Start-Process -FilePath 'C:\Program Files\Docker\Docker\Docker Desktop.exe'
```

Windows에 `docker.exe`가 설치되어 있다는 것과 컨테이너를 실행하는 Docker Engine이 동작 중이라는 것은 별개다. `docker.exe`는 요청을 보내는 클라이언트이고, Docker Desktop 내부의 Linux Engine은 이미지·컨테이너·네트워크·볼륨을 실제로 관리하는 서버다.

Windows에서 Linux 컨테이너를 선택하면 Docker Desktop은 WSL 2 내부의 `docker-desktop` 환경에서 Linux Engine을 시작하고 `dockerDesktopLinuxEngine` named pipe를 만든다. Windows의 Docker CLI는 이 pipe를 통해 Engine API를 호출한다. Engine이 꺼져 있으면 pipe가 존재하지 않으므로 다음 오류가 발생한다.

```text
failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine
```

`Start-Process`는 프로그램 시작만 요청하고 종료를 기다리지 않으므로 성공해도 일반적으로 출력이 없다. PowerShell의 `>>`는 진행 표시가 아니라 앞선 명령이 완성되지 않아 추가 입력을 기다리는 continuation prompt다. 이때는 `Ctrl+C`로 취소하고 명령을 한 줄로 다시 실행한다.

### 9.2 Docker Engine 상태를 확인한 이유

```powershell
docker version
docker info
```

`docker version`은 Client와 Server가 모두 응답하는지 확인한다. Client만 나오면 CLI는 설치됐지만 Engine 연결은 실패한 것이다. `docker info`는 Engine의 상세 상태를 조회한다.

이번 확인에서 Server 29.4.0, Linux/x86_64, WSL 2 커널, containerd snapshotter와 실행 중인 컨테이너가 표시됐다. 이는 Windows CLI에서 WSL 2 내부 Linux Engine까지 API 통신이 정상이라는 의미다.

### 9.3 프로젝트 인프라를 실행하는 명령

```powershell
cd C:\Codex\dev\spring-fullstack-starter
docker compose up -d
docker compose ps
```

`cd`는 현재 디렉터리를 저장소 루트로 옮긴다. Docker Compose는 기본적으로 현재 디렉터리의 `compose.yaml`을 찾으므로 실행 위치가 중요하다.

`docker compose up -d`의 내부 동작은 다음과 같다.

1. `compose.yaml`을 읽어 PostgreSQL과 Redis 서비스 정의를 해석한다.
2. 로컬에 이미지가 없으면 registry에서 `postgres:17-alpine`, `redis:8-alpine`을 내려받는다.
3. `spring-fullstack` 전용 네트워크와 PostgreSQL 영속 볼륨을 만든다.
4. 각 이미지로 컨테이너를 생성하고 포트 `5432`, `6379`를 Windows localhost에 연결한다.
5. `-d` 옵션에 따라 컨테이너를 백그라운드에서 실행하고 PowerShell 프롬프트를 반환한다.

`docker compose ps`는 Compose가 관리하는 컨테이너의 상태와 포트를 조회한다. `healthy`는 프로세스가 단순히 살아 있는 것뿐 아니라 `pg_isready` 또는 `redis-cli ping` health check까지 통과했다는 뜻이다.

PostgreSQL의 데이터는 named volume에 저장되므로 컨테이너를 다시 만들어도 유지된다. 단, `docker compose down -v`는 컨테이너와 함께 이 볼륨도 삭제하므로 초기화를 의도할 때만 사용한다.

### 9.4 백엔드 테스트를 실행하는 명령

```powershell
.\backend\gradlew.bat -p backend test
```

`gradlew.bat`은 저장소에 포함된 Gradle Wrapper다. 개발자마다 전역 Gradle 버전이 달라도 프로젝트가 지정한 Gradle 9.5.1을 내려받아 동일한 빌드를 수행한다.

`-p backend`는 Gradle 프로젝트 디렉터리를 `backend`로 지정하고 `test`는 컴파일, 테스트 리소스 처리, 테스트 클래스 컴파일, JUnit 실행을 의존 순서대로 수행한다. 통합 테스트의 `@ServiceConnection`은 Testcontainers가 임시 PostgreSQL 컨테이너를 만들고 JDBC 접속 정보를 Spring Boot에 자동 전달하게 한다. 테스트가 끝나면 임시 컨테이너는 제거된다. 루트 Compose의 개발 DB와 테스트 DB는 서로 독립적이다.

### 9.5 백엔드를 실행하는 명령

```powershell
.\backend\gradlew.bat -p backend bootRun
```

`bootRun`은 Spring Boot 애플리케이션을 개발 모드로 실행한다. 시작 과정에서 다음 일이 일어난다.

1. `application.properties`와 환경 변수를 읽는다.
2. `localhost:5432`의 PostgreSQL에 연결한다.
3. Flyway가 migration 이력을 확인하고 `V1__create_todo.sql`을 필요한 경우 한 번만 적용한다.
4. Hibernate가 Entity와 실제 스키마가 일치하는지 검증한다. 스키마를 직접 변경하지는 않는다.
5. Spring Security filter chain, Todo API, Actuator를 구성한다.
6. 내장 웹 서버가 기본 포트 `8080`에서 요청을 기다린다.

이 PowerShell 창은 서버 프로세스가 실행되는 동안 점유된다. 종료할 때는 `Ctrl+C`를 누른다.

첫 `bootRun`에서는 Gradle 작업 디렉터리가 `backend`인 반면 Compose 파일은 모노레포 루트에 있어 `No Docker Compose file found`로 중단됐다. `spring.docker.compose.file=../compose.yaml`을 추가해 루트 Compose 파일을 명시했다. `spring.docker.compose.lifecycle-management=start-only`도 지정해 Spring Boot가 필요할 때 인프라를 시작하되 애플리케이션 종료 시 PostgreSQL과 Redis를 함께 종료하지 않도록 했다. 모노레포의 공유 인프라는 백엔드 프로세스 생명주기와 분리하는 편이 개발 중 재시작과 데이터 확인에 유리하다.

### 9.6 프론트엔드를 실행하는 명령

```powershell
npm.cmd run dev --prefix frontend
```

`--prefix frontend`는 현재 위치를 바꾸지 않고 `frontend/package.json`의 `dev` script를 실행한다. 이 script는 Vite 개발 서버를 시작한다. Windows PowerShell에서는 실행 정책이 `npm.ps1`을 차단할 수 있으므로 시스템 정책을 완화하지 않고 `npm.cmd`를 명시적으로 호출한다.

Vite는 기본적으로 `http://localhost:5173`에서 React 화면을 제공하고 소스 변경 시 HMR로 브라우저를 빠르게 갱신한다. 프론트에서 `/api` 또는 `/actuator`로 요청하면 `vite.config.ts`의 proxy가 이를 `http://localhost:8080`의 Spring Boot로 전달한다. 브라우저가 서로 다른 origin에 직접 요청하지 않으므로 로컬 개발 중 CORS 설정 부담도 줄어든다.

### 9.7 전체 요청 흐름

```text
Browser :5173
  -> Vite development server
  -> /api, /actuator proxy
  -> Spring Boot :8080
  -> Spring Security
  -> Controller / JPA
  -> PostgreSQL :5432
```

Redis는 `6379`에서 준비되어 있지만 현재 애플리케이션 코드에서는 아직 사용하지 않는다. 캐시나 분산 세션 요구사항이 결정됐을 때 Spring Data Redis와 정책을 함께 추가할 예정이다.

### 9.8 종료와 재실행

프론트와 백엔드는 각각 실행 중인 PowerShell에서 `Ctrl+C`로 종료한다. PostgreSQL과 Redis는 다음 명령으로 정지하고 컨테이너를 제거한다.

```powershell
docker compose down
```

데이터 볼륨은 유지되므로 다음 `docker compose up -d`에서 기존 데이터가 다시 연결된다. 실행 중인 컨테이너만 잠시 멈추고 싶다면 `docker compose stop`, 다시 시작하려면 `docker compose start`를 사용한다.
